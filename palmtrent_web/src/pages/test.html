7. Key Integrations

7.1 Mirth Connect Integration Architecture

Overview

Mirth Connect serves as the healthcare integration engine, processing HL7 v2.x and FHIR messages between medical devices, hospital systems, and the IthalaMed platform.

Channel 1: Device Data Ingestion

Purpose: Receive continuous vital signs and device parameters
Source: HL7 v2.x Listener (Port 6661, MLLP protocol)
Message Types: ORU^R01 (Observation Results), OBX segments
Transformation: HL7 to FHIR Observation resources
Destination: IthalaMed API (HTTPS POST to /v1/observations)
Frequency: Real-time (every 1-5 seconds per device)

Channel 2: Critical Alert Processing

Purpose: Detect critical changes and trigger immediate notifications
Source: Database reader (polls observations every 5 seconds)
Rules Engine:
  • Heart rate: >140 or <40 = Critical
  • BP Systolic: <90 mmHg = Critical
  • SpO2: <88% = Critical
  • Ventilator disconnect = Critical
Destinations: WebSocket (real-time UI), SMS (Twilio), Push notifications (FCM)
Escalation: Bedside nurse → Charge nurse (30s) → Attending (1min) → Supervisor (2min)

Channel 3: DICOM Study Notification

Purpose: Notify IthalaMed when new imaging studies are available
Source: Orthanc Lua script (on-stored-instance.lua)
Trigger: DICOM C-STORE completion from modality
Transformation: Extract metadata (Patient ID, Study UID, Modality, Description)
Destination: IthalaMed API (/v1/imaging/studies) + Push notification to ordering provider

8. Security & Compliance

8.1 HIPAA Compliance Checklist

✅ Implemented Controls

  • Access Control: Unique user IDs, automatic logoff (15 min), emergency access procedures
  • Encryption: Data at rest (AES-256), data in transit (TLS 1.3)
  • Audit Logs: All PHI access logged with immutable audit trail
  • Integrity: Digital signatures for clinical notes, version control
  • Authentication: Multi-factor authentication (MFA) required
  • Authorization: Role-based access control (RBAC)
  • Backup & Recovery: Daily automated backups, 7-day retention

8.2 Role-Based Access Control (RBAC)

Role Key Permissions
Patient View own records, book appointments, request prescriptions, emergency access
Guardian Manage dependent records, book on behalf, view medical history
Attending Physician Full patient access, create/sign notes, order medications/labs/imaging, view device data
Registered Nurse View patient data, create nursing notes, acknowledge device alerts, administer medications
Pharmacist View prescriptions, dispense medications, check interactions, manage inventory
Lab Technician View lab orders, create results, quality control
Radiologist View imaging studies, create reports, mark critical findings
Hospital Admin Staff management, shift scheduling, view audit logs, system configuration

11. Risk Management

11.1 Technical Risks

Risk Impact Probability Mitigation
Medical device integration failure Critical Medium Redundant paths, heartbeat monitoring, auto-failover, weekly testing
DICOM server failure High Low HA deployment (3 nodes), daily backups, DR site
Database corruption Critical Very Low Point-in-time recovery, daily backups, Multi-AZ deployment
Network latency for devices High Medium Local edge computing, data buffering, QoS network policies
API overload Medium Medium Auto-scaling, rate limiting, caching strategy

11.2 Operational Risks

Risk Impact Probability Mitigation
Staff resistance to adoption High Medium Training program, champion users, gradual rollout, 24/7 support
Regulatory non-compliance Critical Low Annual audits, legal review, compliance officer, documentation
Data breach Critical Low Encryption, penetration testing, security audits, incident response plan
Vendor lock-in (cloud) Medium Medium Multi-cloud strategy, containerization, standard protocols
